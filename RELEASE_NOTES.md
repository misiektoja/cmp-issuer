# Release notes

All notable changes to this project are documented in this file.

## [0.1.0] - TBD

First development release of cmp-issuer, a vendor-neutral cert-manager external issuer that enrolls certificates from CMPv2 servers. A cert-manager `Certificate` that references a `CMPIssuer` or `CMPClusterIssuer` is enrolled over CMP with mandatory message protection and the issued certificate lands in the usual TLS Secret. Enrollment is verified end to end against two independent CMP servers, Nokia NCM 26.7 and EJBCA Community Edition 9.3.7, using both PasswordBasedMac and certificate-signature protection. Certificate authorities that queue requests or require manual approval are supported, because an enrollment the server answers with `waiting` is polled to completion and survives a controller restart. An enrollment interrupted mid-flight resumes under its original transaction identifier, so a restart never issues a second certificate. The release ships a Helm chart, a documentation set and attested multi-architecture images.

### Features

* **CMPv2 enrollment through cert-manager** - Add the `CMPIssuer` and `CMPClusterIssuer` resources at `v1alpha1` in the `certmanager.misiektoja.github.io` API group. cert-manager `Certificate` and `CertificateRequest` resources are enrolled over CMP with a PKCS #10 request carried in P10CR. **`initialEnrollment` accepts only `P10CR`**, because IR requires CRMF proof of possession over the workload private key that the issuer never reads.
* **PasswordBasedMac and certificate-signature protection** - Authenticate every CMP message with a shared reference and secret or with an end-entity certificate and key. Protection is mandatory and independent of the transport, so an HTTP endpoint is still authenticated.
* **Asynchronous enrollment that survives restarts** - Enroll against certificate authorities that queue requests or require manual approval. A server that answers **`waiting`** is polled with `pollReq` until it returns the certificate, honoring the wait it asks for within the configured `minimumPollInterval` and `maximumPollInterval` and giving up after `maximumDuration` or `maximumPolls`. Each enrollment is recorded in a `CMPTransaction` before the first message is sent, so a controller restart resumes the pending transaction instead of enrolling a second time. Run `kubectl get cmptransactions -A` to follow enrollment progress.
* **Durable, self-describing transaction records** - Record the **transaction identifier before the first message reaches the network** and the **validated chain before it is returned**, so that no interruption causes a duplicate certificate or a lost one. A controller that stops while an enrollment is unanswered retries under that **original transaction identifier**, instead of generating a new one that the server would accept as an unrelated enrollment. Both tested servers recognize the repeat and answer with an authenticated error, **Nokia NCM 26.7 with `transactionIdInUse` and EJBCA CE 9.3.7 with `badRequest`**, and neither issues a second certificate; the request then fails and cert-manager enrolls again under a new transaction identifier. A controller that stops after the certificate was issued returns the recorded chain without further CMP traffic. Each record also carries the enrolled CSR digest, the issuing `CMPIssuer` or `CMPClusterIssuer`, the CMP operation and the protocol version, so a stalled enrollment can be diagnosed with `kubectl describe cmptransaction` rather than from server-side logs. The phase reports `Enrolling`, `Polling`, `Confirming` or `Issued`. A completed record is kept until its `CertificateRequest` is removed.
* **Delayed confirmation that survives a restart** - Complete enrollment against servers that delay the acknowledgement rather than the certificate and answer `certConf` with `waiting` instead of `pkiConf`. The **validated chain is recorded before `certConf` is sent**, so the transaction reports `Confirming` and is polled to `pkiConf` under the same `spec.transaction` limits as a delayed enrollment. A controller restart during that wait resumes the confirmation rather than failing a request whose certificate already exists. Confirmation is also verified against servers such as NCM that omit `extraCerts` and `senderKID` from the final message, by reusing the response signer already validated when the certificate was accepted.
* **Interoperable P10CR response identifiers** - Accept the `certReqId` value `-1` required by RFC 9810 and RFC 9483 or the value `0` returned by the CMP servers tested so far, echo the received value in `certConf` and reject anything else. Set **`p10crResponseCertReqId`** to pin one value for a server whose behavior is known.
* **HTTP and HTTPS transport** - Configure an explicit endpoint URL with bounded responses, rejected redirects and HTTPS trust that stays separate from CMP response trust. An HTTP issuer reports a one-time readiness warning about missing transport confidentiality.
* **Verified against Nokia NCM and EJBCA** - Complete protected P10CR, CP, `certConf` and `pkiConf` flows through real cert-manager `Certificate` resources against **Nokia NCM 26.7** and **EJBCA Community Edition 9.3.7**, using PasswordBasedMac and certificate-signature protection. EJBCA resolves the signer certificate itself, so `chainKey` may be omitted. EJBCA client mode consumes the enrollment code once per certificate, so an end entity must be returned to `NEW` or allowed multiple requests before it can enroll again.
* **Verified against OpenSSL on every push** - Run the delayed enrollment, delayed confirmation and pinned transaction flows against the CMP mock server built into **OpenSSL 3.6**, a third implementation that shares no code with cmp-issuer or the CMP library behind it. The pinned transaction coverage confirms that the identifier recorded before sending is the identifier OpenSSL saw on the wire. The build fails if that coverage is skipped, so an unavailable or downgraded OpenSSL cannot quietly remove it.
* **Install from a Helm repository** - Add **`https://misiektoja.github.io/cmp-issuer/charts`** and install with `helm install`, without cloning anything. Every release is added to that repository index and older versions stay installable, so `helm search repo cmp-issuer -l` lists what is available. A packaged chart and a self-contained `install.yaml` are attached to each release for offline and non-Helm installs. All paths install the same CRDs, RBAC and Deployment, and none grants Secret access in workload namespaces. The CRDs ship inside the chart so `helm upgrade` updates them, and they are marked to **survive `helm uninstall`** so removing the release cannot delete the issuers and transactions in your cluster.
* **A guided path from an empty cluster to an issued certificate** - Follow **[Getting started](docs/getting-started.md)** through seven steps, each showing the expected output so a wrong turn is obvious immediately. It covers the two permissions that are easy to miss: cert-manager must be allowed to **approve requests for this issuer type**, otherwise every `CertificateRequest` waits forever with no error reported, and the controller must be authorized to read credentials in each namespace. Both are also in [Installation](docs/installation.md) and are the first entries in [Troubleshooting](docs/operations/troubleshooting.md). The README carries the same path for readers who never open the site.
* **Documentation set** - Read installation, architecture, a support matrix, the `CMPIssuer` and `CMPClusterIssuer` reference, transport, message protection, CMP response trust, cert-manager private-key handling, enrollment, transaction recovery, tested PKIs, troubleshooting, the security model and known limitations under [docs/](docs/).

### Security

* **Workload private keys are never read** - For P10CR the controller forwards the signed PKCS #10 request supplied by cert-manager and never reads the workload private key.
* **Namespace-bounded credential access** - The manager ClusterRole carries no Secret access. A `CMPIssuer` reads credential and trust Secrets only in namespaces that carry the RoleBinding described in [credential Secret access](docs/operations/secret-access.md). A `CMPClusterIssuer` reads them only in the controller's cluster resource namespace.
* **Fail-closed response validation** - Verify CSR signatures, CMP response protection, transaction identifiers, nonces, the P10CR `certReqId`, the issued public key and leaf-first certificate chains before a certificate is accepted. A failed transport or a rejected response stores no partial material.
* **Only the authority you addressed can answer** - Require every CMP response to be sent by the authority configured as **`spec.protocol.recipient`**, rejecting anything else with `wrongAuthority`. Trust anchors establish that a responder is trusted rather than which responder answered, so under a shared enterprise or public root any subordinate CA would otherwise satisfy protection verification and could substitute a response. The check applies to shared-secret and certificate-signature protection alike. Distinguished name attributes are compared **ignoring their order**, because certificate tools disagree about whether to print a name in encoded order or in the reverse order RFC 4514 defines, so a recipient copied from either kind of output keeps working. A response that sends no sender name, which RFC 4210 permits, is accepted on its protection alone.
* **Supply chain reporting** - Every push and a weekly schedule report vulnerable dependencies, credentials leaked into the working tree or the full commit history, container image findings and a CycloneDX bill of materials.
* **Attested release artifacts** - Publish a **multi-architecture image for `linux/amd64` and `linux/arm64` to the GitHub Container Registry with a build provenance attestation**, alongside the installer manifest, the bill of materials and the packaged Helm chart.

### Known limitations

The API group is served at `v1alpha1` and may change. Renewal reissues through P10CR rather than CMP Key Update Request. Transaction state persistence has documented gaps. See [known limitations](docs/known-limitations.md) before relying on this release in production.
