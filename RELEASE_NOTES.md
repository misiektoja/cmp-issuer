# Release notes

All notable changes to this project are documented in this file.

## [0.1.0] - TBD

First development release of cmp-issuer, a vendor-neutral cert-manager external issuer that enrolls certificates from CMPv2 servers. A cert-manager `Certificate` referencing a `CMPIssuer` or `CMPClusterIssuer` is enrolled over CMP with mandatory message protection, and the certificate lands in the usual TLS Secret. Certificate authorities that queue requests or require manual approval are supported: enrollment polls to completion, survives a controller restart, and never issues a duplicate certificate. The release ships a Helm chart, a documentation set and attested multi-architecture images.

### Features

* **CMPv2 enrollment through cert-manager** - Adds the `CMPIssuer` and `CMPClusterIssuer` resources at `v1alpha1` in the `certmanager.misiektoja.github.io` API group. `Certificate` and `CertificateRequest` resources enroll over CMP using a PKCS #10 request (P10CR). **`initialEnrollment` accepts only `P10CR`**, because IR requires proof of possession over the workload private key, which the issuer never reads.
* **PasswordBasedMac and certificate-signature protection** - Authenticate every CMP message with a shared reference and secret, or with an end-entity certificate and key. Protection is mandatory and independent of transport.
* **Asynchronous enrollment that survives restarts** - Enroll against CAs that queue requests or require manual approval. A `waiting` response is polled with `pollReq` until the certificate is ready, honoring the server's requested interval within `minimumPollInterval`/`maximumPollInterval`, and giving up after `maximumDuration` or `maximumPolls`. Each enrollment is recorded in a `CMPTransaction` before the first message is sent, so a restart resumes it instead of enrolling twice. Track progress with `kubectl get cmptransactions -A`.
* **Durable transaction records prevent duplicate or lost certificates** - The transaction identifier is recorded before the first message is sent and the validated certificate chain before it is returned. A restart before issuance resumes the same transaction instead of starting a new one; if the server no longer recognizes it, the attempt fails safely and cert-manager retries under a new transaction. A restart after issuance returns the recorded chain with no further CMP traffic. Each record also carries the CSR digest, the issuing `CMPIssuer`/`CMPClusterIssuer`, the operation and protocol version, and its phase (`Enrolling`, `Polling`, `Confirming`, `Issued`), so `kubectl describe cmptransaction` is enough to diagnose a stalled enrollment.
* **Delayed confirmation survives restarts too** - For servers that acknowledge asynchronously (`certConf` answered with `waiting` instead of `pkiConf`), the validated chain is recorded before `certConf` is sent, so a restart resumes confirmation instead of re-enrolling a certificate that already exists. This also works against servers, such as NCM, that omit `extraCerts` and `senderKID` from the final message, by reusing the signer already validated when the certificate was accepted.
* **Interoperable P10CR response identifiers** - Accepts the RFC-required `certReqId` value `-1`, or the `0` some CMP servers return instead, and echoes the received value back in `certConf`. Set **`p10crResponseCertReqId`** to pin one value for a server with known behavior.
* **HTTP and HTTPS transport** - Configure an explicit endpoint URL with bounded responses, rejected redirects, and HTTPS trust kept separate from CMP response trust. An HTTP issuer reports a one-time readiness warning about the missing transport confidentiality.
* **Verified against Nokia NCM and EJBCA** - Protected P10CR, CP, `certConf` and `pkiConf` flows are exercised end to end through real cert-manager `Certificate` resources against **Nokia NCM 26.7** and **EJBCA Community Edition 9.3.7**, with both protection mechanisms. EJBCA resolves the signer certificate itself, so `chainKey` may be omitted; its client mode consumes an enrollment code once per certificate, so the end entity must be reset to `NEW` or allowed multiple requests before enrolling again.
* **Verified against OpenSSL on every push** - The CMP mock server built into **OpenSSL 3.6**, which shares no code with cmp-issuer or its underlying library, exercises delayed enrollment, delayed confirmation and pinned transaction identifiers on every push. The build fails if this coverage is skipped.
* **Install from a Helm repository** - Add **`https://misiektoja.github.io/cmp-issuer/charts`** and install with `helm install`, without cloning anything. A packaged chart and a self-contained `install.yaml` are attached to each release too. CRDs ship inside the chart, so `helm upgrade` updates them, and they are marked to **survive `helm uninstall`**, so removing the release cannot delete the issuers and transactions in your cluster.
* **Pre-authorize credential namespaces from the chart** - List namespaces in **`credentialNamespaces`** and the chart creates the RoleBinding each one needs, instead of applying it by hand. The controller still holds no cluster-wide Secret access; only the namespaces you name become readable.
* **cert-manager approval works out of the box** - Install grants cert-manager's built-in approver permission to approve requests for this issuer type; without it, every `CertificateRequest` waits forever with no visible error. Point it at a non-default installation with `certManagerApproval.serviceAccountName`/`certManagerApproval.namespace`, or set **`certManagerApproval.create=false`** when approver-policy decides instead.
* **A guided path from an empty cluster to an issued certificate** - Follow **[Getting started](docs/getting-started.md)** through six steps with expected output at each one, or use [Troubleshooting](docs/operations/troubleshooting.md), organized by the symptom you see.
* **Documentation set** - Installation, architecture, a support matrix, the `CMPIssuer`/`CMPClusterIssuer` reference, transport, message protection, CMP response trust, cert-manager private-key handling, enrollment, transaction recovery, tested PKIs, troubleshooting, the security model and known limitations, all under [docs/](docs/).

### Security

* **Workload private keys are never read** - For P10CR the controller forwards the signed PKCS #10 request from cert-manager and never reads the workload private key.
* **Namespace-bounded credential access** - The manager ClusterRole carries no Secret access. A `CMPIssuer` reads credential and trust Secrets only in namespaces granted the RoleBinding described in [credential Secret access](docs/operations/secret-access.md); a `CMPClusterIssuer` reads them only in the controller's own namespace.
* **Fail-closed response validation** - CSR signatures, CMP response protection, transaction identifiers, nonces, the P10CR `certReqId`, the issued public key and leaf-first certificate chains are all verified before a certificate is accepted. A failed transport or a rejected response stores no partial material.
* **Only the authority you addressed can answer** - Every CMP response must come from the authority configured as **`spec.protocol.recipient`**, rejected otherwise with `wrongAuthority`. Trust anchors only establish that a responder is trusted, not which one answered, so under a shared trust anchor any subordinate CA could otherwise substitute a response; the check applies to both protection mechanisms. Distinguished name attributes are compared ignoring order, so a recipient copied from either RFC 4514 ordering still works, and a response with no sender name, which RFC 4210 permits, is accepted on its protection alone.
* **Supply chain reporting** - Every push and a weekly schedule report vulnerable dependencies, leaked credentials in the working tree or commit history, container image findings, and a CycloneDX bill of materials.
* **Attested release artifacts** - Multi-architecture images for **`linux/amd64`** and **`linux/arm64`** are published to the GitHub Container Registry with a build provenance attestation, alongside the installer manifest, bill of materials and packaged Helm chart.

### Known limitations

The API group is served at `v1alpha1` and may change. Renewal reissues through P10CR rather than CMP Key Update Request. Transaction state persistence has documented gaps. See [known limitations](docs/known-limitations.md) before relying on this release in production.
