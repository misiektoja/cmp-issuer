# Release notes

All notable changes to this project are documented in this file.

## [0.1.0] - TBD

First release of cmp-issuer, a vendor-neutral cert-manager external issuer that speaks CMPv2 directly to a certificate authority. Point a cert-manager `Certificate` at a `CMPIssuer` or `CMPClusterIssuer` and cert-manager generates the private key and the PKCS #10 request, cmp-issuer enrolls it over CMP as a **P10CR** and the issued certificate is written to the usual TLS Secret, so workloads that already consume cert-manager Secrets need no change. **Renewal takes the same path**, a fresh P10CR rather than a CMP Key Update Request. Every CMP message is authenticated in both directions, with a shared secret or a certificate signature, over HTTP or HTTPS. Authorities that queue requests or require manual approval are polled to completion. An enrollment interrupted by a controller restart resumes under its original transaction instead of starting a second one. Issuance was verified end to end against **Nokia NCM 26.7** and **EJBCA Community Edition 9.3.7**. Runs on Kubernetes v1.34 to v1.36 with cert-manager v1.19 to v1.21. Licensed under Apache-2.0.

This is an early release. The API group is served at `v1alpha1` and may change. The CMP surface is deliberately narrow and several operational features are still on the roadmap, so read the known limitations below and the fuller [known limitations](https://misiektoja.github.io/cmp-issuer/known-limitations/) page before relying on this release in production.

### Features

* **CMPv2 enrollment through cert-manager** - Adds `CMPIssuer` (namespaced) and `CMPClusterIssuer` (cluster-wide) at `v1alpha1` in the `certmanager.misiektoja.github.io` API group. The subject, subject alternative names and public key of the cert-manager `Certificate` travel in the PKCS #10 request, the only mode **`initialEnrollment`** accepts, because the alternative requires proof of possession over a private key this issuer never reads. Explicit `certConf` confirmation is the default and server-granted implicit confirmation is available through **`protocol.confirmation: Implicit`**. See [enrollment](https://misiektoja.github.io/cmp-issuer/guide/enrollment/).
* **Renewal reissues through P10CR** - cert-manager renewal was verified against **Nokia NCM 26.7** for both values of **`privateKey.rotationPolicy`**. The controller read no private key in either case. This is **re-enrollment, not CMP Key Update Request**, so it fails against a server whose profile authorizes an identity to enroll only once. See [renewal and KUR](https://misiektoja.github.io/cmp-issuer/guide/renewal-and-kur/).
* **Mandatory message protection** - Authenticate every CMP message with **PasswordBasedMac** from a shared reference and secret, with a configurable one-way function, MAC and iteration count or with a **certificate signature** from an end-entity certificate and key. Protection is required regardless of transport, so HTTP and HTTPS both authenticate. An HTTP issuer reports a one-time readiness warning about the missing confidentiality. See [message protection](https://misiektoja.github.io/cmp-issuer/guide/message-protection/).
* **Enrollment completes even when the CA answers slowly** - Authorities that queue requests or require manual approval are polled until the certificate is ready, bounded by **`maximumDuration`**, **`maximumPolls`** and a poll interval range. A confirmation the server defers is polled the same way. A controller restart mid-enrollment resumes the same request rather than starting a second one. A restart after issuance returns the certificate already obtained. Watch progress with `kubectl get cmptransactions -A` and diagnose a stalled request with `kubectl describe cmptransaction`. See [transaction recovery](https://misiektoja.github.io/cmp-issuer/guide/transaction-recovery/).
* **Transport you can constrain** - Reach the endpoint over HTTPS with a custom trust anchor or with the system trust store, where **TLS trust is configured separately from CMP trust**. Bound each exchange with a **`timeout`** and a **`maxResponseSize`**. Redirects are never followed, so a server cannot move an enrollment to another host. See [transport](https://misiektoja.github.io/cmp-issuer/guide/transport/).
* **Server-modified certificates are refused by default** - An authority that rewrites the requested identity answers `grantedWithMods`. **`policy.grantedModifications: Reject`** fails that enrollment rather than storing a certificate that does not carry what was asked for. Set `Accept` where the certificate authority is expected to own the subject.
* **Verified against Nokia NCM and EJBCA** - Real `Certificate` resources were issued end to end against **Nokia NCM 26.7** and **EJBCA Community Edition 9.3.7** with both protection mechanisms and **over HTTPS as well as HTTP**, with the endpoint certificate verified against a pinned authority that did not sign the CMP responses. EJBCA was verified in both a **client mode** and an **RA mode** alias, which matters because client mode authorizes an identity to enroll only once and RA mode registers the end entity from the request instead. Enrollment against EJBCA runs in CI on every change, so the interoperability claim is re-checked continuously rather than once. Per-server setup notes are in [tested PKIs](https://misiektoja.github.io/cmp-issuer/interoperability/tested-pkis/).
* **Three ways to install** - Add the Helm repository at **`https://misiektoja.github.io/cmp-issuer/charts`**, apply the self-contained **`cmp-issuer-<version>-install.yaml`** or unpack the **air-gapped bundle** attached to each release, which carries the manager image as an OCI archive next to the chart, the installer manifest and the **bill of materials**, so a cluster with no route to the release page can still audit what it is installing. CRDs ship inside the chart so `helm upgrade` updates them. They also **survive `helm uninstall`**, so removing the release cannot delete your issuers and transactions. The chart declares **`kubeVersion: >= 1.31.0-0`**, so a cluster older than the verified v1.34 to v1.36 range can still install at its own risk. The chart is listed with full metadata in catalogs such as Artifact Hub. See [installation](https://misiektoja.github.io/cmp-issuer/installation/).
* **Chart values for the settings that otherwise block issuance** - **`credentialNamespaces`** creates the RoleBinding each namespace needs for its credential Secrets, so the controller never gains cluster-wide Secret access. **`CMPClusterIssuer` credentials are read from the release namespace**, whatever it is called. **`manager.clusterResourceNamespace`** moves that lookup and its RoleBinding together when those Secrets live elsewhere. **`certManagerApproval`** grants cert-manager's built-in approver permission over this issuer type, without which every `CertificateRequest` waits forever with no visible error. Set **`certManagerApproval.create=false`** when approver-policy decides instead.
* **Chart values for the shape of the deployment** - **`rbac.namespaced`** installs the controller with Role and RoleBinding in one namespace instead of cluster-wide RBAC. **`rbac.helpers`** installs admin, editor and viewer roles for the issuer kinds so you can delegate access without writing RBAC by hand. **`logging.level`**, **`logging.stacktraceLevel`** and **`logging.encoder`** shape controller output without knowing the underlying flag names. **`metrics`** serves the controller-runtime and Go metrics over HTTPS on port 8443, with an optional Prometheus **`ServiceMonitor`** and an optional **`NetworkPolicy`** in front of it. The manager pod runs under restricted Pod Security defaults: non-root, no privilege escalation, all capabilities dropped and a read-only root filesystem.
* **`kubectl logs` explains an issuance** - Each completed enrollment writes one **`Issued certificate`** line carrying the subject, serial number, validity window, subject alternative names, key details and issuing CA, so you can answer what was issued without decoding the Secret or reaching the CMP server. A queued enrollment reports each wait and its deadline. A rejection names the typed CMP failure. The log never carries credential values, private keys or CSR bodies.
* **Guided setup and symptom-based troubleshooting** - [Getting started](https://misiektoja.github.io/cmp-issuer/getting-started/) goes from an empty cluster to an issued certificate in six steps with the expected output at each one. [Troubleshooting](https://misiektoja.github.io/cmp-issuer/operations/troubleshooting/) is organized by the symptom you actually see. Full documentation is at [misiektoja.github.io/cmp-issuer](https://misiektoja.github.io/cmp-issuer/).

### Security

* **Workload private keys are never read** - The controller forwards the signed PKCS #10 request from cert-manager and never touches the private key cert-manager generated. See [private-key handling](https://misiektoja.github.io/cmp-issuer/guide/private-key-handling/).
* **Namespace-bounded credential access** - The manager ClusterRole carries no Secret access at all. A `CMPIssuer` reads credential and trust Secrets only in namespaces you explicitly grant. A `CMPClusterIssuer` reads them only in the controller's own namespace. See [credential Secret access](https://misiektoja.github.io/cmp-issuer/operations/secret-access/).
* **Fail-closed response validation** - CSR signatures, response protection, transaction identifiers, nonces, the issued public key and certificate chains are all verified before a certificate is accepted. A failed transport or a rejected response stores no partial material. Every response must also come from the authority configured as **`spec.protocol.recipient`**, so a subordinate CA under a shared trust anchor cannot substitute an answer. See [CMP response trust](https://misiektoja.github.io/cmp-issuer/guide/cmp-response-trust/).
* **Hardened CMP verification path** - The CMP encoding dependency is pinned to a **reviewed branch** rather than to its published release, which accepted a signature-protected response from any certificate chaining to the configured trust anchor without matching the sender the message claimed and returned an issued certificate without checking that it certifies the key that was requested. The branch also corrects CMP media type parsing, CMP-over-HTTP error handling and response nonce validation on a delayed delivery. It also bounds the poll interval a server can ask for. The exact version is named in the bill of materials attached to the release. See [ADR 0001](https://misiektoja.github.io/cmp-issuer/adr/0001-cmp-library/).
* **Attested, inspectable release artifacts** - Multi-architecture images for **`linux/amd64`** and **`linux/arm64`** are published to the GitHub Container Registry with a build provenance attestation, alongside a **CycloneDX bill of materials** that records a resolved license for every module in the build. Every push and a weekly schedule report vulnerable dependencies, leaked credentials, container image findings and **CodeQL static analysis** results. See [provenance](https://misiektoja.github.io/cmp-issuer/provenance/).

### Known limitations

* **The protocol surface is narrow** - Enrollment and renewal both use P10CR. **IR with CRMF**, **true KUR**, **PBMAC1**, **CMPv3**, **revocation over CMP** and **mTLS to the CMP endpoint** are planned rather than implemented. Kubernetes CSR signing is unsupported by design. Compatibility depends on each server's CMP profile, so broad CMP compatibility is not claimed. See [support matrix](https://misiektoja.github.io/cmp-issuer/support-matrix/).
* **`Certificate.spec.duration` is not requested** - A PKCS #10 request carries no validity, so the certificate authority alone decides the lifetime of the issued certificate. Requesting a duration needs CRMF and arrives with it.
* **A lost enrollment response cannot be recovered** - If the response never arrives, the retry under the recorded transaction identifier reliably prevents a second certificate for that attempt. Neither tested server returns the certificate it already issued. The `CertificateRequest` fails, cert-manager enrolls again under a new transaction and the earlier certificate is orphaned, counting against any issuance quota or audit trail the authority keeps.
* **Credential rotation during an open transaction is not detected** - Rotating a PasswordBasedMac or signature Secret while a transaction is in flight is noticed when the server rejects the new protection or when `maximumDuration` elapses, not at the moment of rotation.
* **Completed transactions are retained** - A `CMPTransaction` that obtained a certificate keeps its record so that a restart cannot enroll a second time. It is removed only when the owning `CertificateRequest` is garbage collected, so completed transactions are listed next to in-flight ones.
* **No issuance metrics yet** - The controller exposes the standard controller-runtime and Go metrics only, so enrollment counts, durations and failure reasons come from the log rather than from a dashboard or an alert.
* **Readiness reflects configuration, not reachability** - An issuer whose endpoint is unreachable still reports `Ready`. The first enrollment is where a wrong URL surfaces. An issuer names one endpoint and there is no failover to a second.
* **Install from a release artifact or a checkout** - The CMP encoding dependency is redirected to the reviewed fork by a `replace` directive, which Go ignores for `go install` at a version and for anyone importing cmp-issuer as a library, so those routes silently build against the unfixed upstream.
* **The API may change** - `certmanager.misiektoja.github.io/v1alpha1` is an alpha API and both issuer kinds are experimental.
